i. Discovery questions

Discovery.

— Spend the first 15 minutes asking, not designing. Most candidates skip this and dive straight into boxes. Don't be that candidate. Stakeholder alignment is graded as much as the architecture itself.

Users & Scope Who's using this, and what does success look like?
  • Who are the end users — internal employees only, or contractors and vendors too?
  • What roles are we automating for? Sales? Operations? All of engineering?
  • What are the top 3 tasks we'd automate first? (We can't build everything; let's prioritize.)
  • What does success look like — time saved per task? % of tasks fully automated? Adoption rate?
  • Is there an MVP scope vs. full vision?
Why it matters Anchors the design to a measurable outcome. Without metrics, you can't make tradeoffs later (latency vs. cost, autonomy vs. safety).
Data & Sensitivity What data is involved, and how sensitive is it?
  • What data sources will the agent need? CRM, email, spreadsheets, internal databases, web?
  • Which of those contain PII? Which are regulated (financial, health)?
  • What jurisdictions is data subject to? GDPR? CCPA? HIPAA? Regional residency?
  • Is there data we are not allowed to send to third-party LLMs?
  • What's the data retention policy — how long do we keep prompts, responses, audit trails?
Why it matters Drives every architectural decision around isolation, encryption, and which model we can use. Sensitive data → self-hosted or in-VPC inference; otherwise → managed APIs.
Scale & Performance How big does this get, and how fast must it be?
  • How many active users — 10K? 100K? 1M?
  • Traffic patterns — steady, or burst (Monday mornings, end-of-quarter)?
  • What's an acceptable latency — sub-second, ~3 sec, can be async (background)?
  • How many automated tasks per user per day on average?
  • What's the SLA — 99.9%? 99.99%? Business-hours only?
Why it matters Determines whether to design for synchronous interactive use (chat-style) or asynchronous batch (queue-based). Big difference in architecture.
Autonomy & Safety How much should the agent do on its own?
  • Should the agent execute actions (send emails, modify records) or only draft them for human approval?
  • What's the blast radius of a mistake — can it be undone? Customer-facing or internal-only?
  • Are some action types high-risk and require explicit approval (financial, customer comms)?
  • What's the appetite for false positives vs. false negatives?
  • What audit trail do compliance/legal need to see?
Why it matters Defines the human-in-the-loop layer. "Send email autonomously" and "draft email for review" are completely different products with different architectures.
Existing Stack & Constraints What's already in place, and what are the constraints?
  • What cloud provider(s) — GCP, AWS, Azure, multi-cloud?
  • What SSO / IAM are we integrating with?
  • Are there existing chatbots or RPA tools we're replacing or augmenting?
  • What's the budget envelope — both build and run cost?
  • Build vs. buy — open to managed services (Vertex AI Agent Builder, Bedrock Agents) or strict on building from primitives?
  • Timeline to first production deployment?
Why it matters Real engineering happens within constraints. Knowing the existing stack and budget shapes 80% of the technical decisions.
ii. Architecture & reasoning

Architecture.

— Reference architecture for a multi-tenant agentic workflow automation platform on GCP. Each layer is annotated with the reasoning behind the choice and the GCP product that implements it.

Component breakdown

01API Gateway + IAM

Single entry point for all employee requests. Authenticates via SSO, injects user identity into every downstream call. Rate-limits per user/tenant.

WhyAuthentication and rate limiting at the edge keeps the agent layer simple and prevents noisy-neighbor abuse.

Cloud Endpoints · IAM · IAP
02Agent Orchestrator

Stateless service running the agent loop (ReAct: reason → call tool → observe → repeat). Splits internally into Planner, Executor, and Memory.

WhyStateless on Cloud Run autoscales horizontally for spiky traffic. Conversation state is externalized to Firestore so any instance can resume any session.

Cloud Run · Vertex AI Agent Builder
03Tool Registry

Each tool is a typed function the LLM can decide to call. Tools have schemas (name, params, return type), least-privilege scopes, and per-tool rate limits.

WhyAdding a new automation = adding a new tool. The orchestrator code stays unchanged. Open/closed principle at the system level.

Cloud Run / Cloud Functions per tool
04LLM Serving — Model Routing

Default to Gemini Flash (fast, cheap). Escalate to Gemini Pro only for complex reasoning steps. Fallback to a secondary provider if Vertex is degraded.

WhyModel routing typically cuts ~60-80% of token cost without hurting quality, since most steps are simple.

Vertex AI · Gemini Flash + Pro
05RAG Pipeline

Internal docs are chunked at ingest (semantic or fixed-size), embedded with a managed model, indexed in Vertex Vector Search. Retrieval pulls top-k, rerankers score relevance, top-N is stuffed into the prompt with citations.

WhyGrounding is the single biggest hallucination defense. Citations also enable groundedness scoring.

Vertex Vector Search · BigQuery
06Approval Queue / HITL

Default mode: agent drafts; human approves. Confidence threshold + action-type policy decide whether to auto-execute. High-risk actions (external comms, financial) always queue.

WhyReduces blast radius dramatically. The "agent that never sent a wrong email" is the agent that drafted before sending.

Pub/Sub · Custom reviewer UI
07Eval & Guardrails

Output filters (safety classifiers, PII leakage detection). Groundedness scoring (does the answer cite retrieved docs?). Continuous eval suite triggered on prompt or model changes.

WhyWithout eval you have no objective answer to "is the agent getting better or worse?" Critical for production.

Vertex AI Eval · Langfuse
08Vector Search (RAG store)

Stores document embeddings + metadata for semantic retrieval. Per-tenant namespacing prevents cross-tenant leakage at the DB level.

WhyTenant isolation must be defense-in-depth — at IAM, at the application, AND at the data layer.

Vertex Vector Search · Pinecone · Weaviate
09Conversation State

Per-user-per-session message history. Externalizing this from the orchestrator is what makes the orchestrator stateless and horizontally scalable.

WhyLets us treat agent instances as cattle, not pets. Restart a pod, traffic re-routes, no session loss.

Firestore · Cloud SQL
10Async Queue

Long-running tasks (market research, batch processing) get queued instead of held synchronously. Workers pull from queue, run independently, post results back via webhook or push.

WhyDecouples user-facing latency from actual work duration. Survives traffic spikes by buffering.

Pub/Sub · Cloud Tasks
11Audit / Analytics

Every prompt, every tool invocation, every model response, every approval decision is logged. PII redacted via Cloud DLP before storage.

WhyCompliance + debuggability + analytics. "What did the agent do at 3pm yesterday?" must always be answerable.

BigQuery · Cloud Logging
12Security & Observability

Cloud DLP redacts PII at every ingress. KMS-backed CMEK encrypts data at rest. VPC Service Controls enforce a network perimeter. Distributed tracing follows a request through agent → tool → LLM → DB.

WhySecurity and observability aren't "added later." They're foundational and shape every other component.

Cloud DLP · KMS · VPC SC · Cloud Trace

Key tradeoffs to call out explicitly

Hosted LLM vs. self-hosted
Hosted (Vertex/Gemini) → faster to ship, scales automatically, but data residency must be acceptable. Self-hosted (vLLM in VPC) → full control, slower iteration, higher infra cost. Default to hosted unless data sensitivity forbids it.
Autonomy vs. safety
Full autonomy is the demo dream; draft-then-approve is the production reality. Start with approval-required for everything; relax per action type as confidence grows from real metrics.
RAG vs. fine-tuning
RAG is cheaper, faster to update, and more transparent (citations). Fine-tuning is for style/format, not for facts. Default to RAG; layer fine-tuning later only if a quality gap remains.
Latency vs. cost
Multi-step agent loops can take 5-30 seconds. For interactive UX, run shorter loops and async-queue the longer tasks. Cost scales with steps × tokens × model size — model routing is the biggest lever.
Synchronous vs. asynchronous
Chat-style interactions need sub-3-second response. Background research / batch tasks belong in Pub/Sub. Architecting for both from day one avoids painful refactors.
iii. Customer Q&A

Q&A.

— Real questions you'll get from clients (and likely from interviewers, too). Click to expand each.

Filter All Security Cost Operations Quality Delivery
How do you handle our sensitive data and PII?Security

Five layers of defense:

  • Data residency: VPC Service Controls keep data in a defined region/perimeter. Inference happens in the same region; no cross-region leakage.
  • PII redaction at ingest: Cloud DLP scans uploads and redacts/tokenizes PII before storage or model invocation.
  • Encryption: All data at rest is CMEK-encrypted (customer-managed keys via Cloud KMS). All in-transit is TLS.
  • Tenant isolation: Per-tenant namespaces in the vector DB and per-tenant IAM scopes. Defense-in-depth — application logic plus DB-level enforcement.
  • Audit: Every prompt, retrieval, and model output is logged with user identity and timestamp.
Critically: data sent to Vertex AI is not used to train Google's foundation models. That's contractually guaranteed.
What if the agent sends a wrong email or modifies the wrong record?Quality

Three layers of safety:

  • Default mode is draft, not send. The agent prepares a draft; a human reviews and approves before any external communication. We graduate specific action types to autonomous execution only after sustained accuracy in production.
  • Confidence thresholds. Below a threshold, the action queues for review automatically. Above, it executes. Threshold is per action type — sending an internal Slack might be 80%; sending an external client email might be 99%.
  • Audit + rollback. Every action is logged with full context (input, retrieved docs, reasoning trace, output). Most actions are reversible (delete an email draft, revert a record); for irreversible actions we require explicit human confirmation.
How do you prevent the agent from hallucinating?Quality

Hallucinations are a probability problem, not a binary one. We attack it from four angles:

  • RAG grounding: Every factual claim must trace to a retrieved document. The agent is prompted to cite sources; outputs without citations are flagged.
  • Groundedness scoring: An automated check verifies that each cited source actually supports the claim. Outputs failing this score are rejected or queued.
  • Eval suite: Curated test cases run on every prompt or model change. We track pass-rate over time and gate deployments.
  • Human-in-the-loop: Low-confidence outputs are reviewed before action. Reviewer feedback feeds back into our eval suite.
No system fully eliminates hallucinations. We design for graceful degradation: prefer "I don't know — let me find a human" over a confident wrong answer.
How does this scale to our 50,000 employees?Ops
  • Stateless agent service on Cloud Run autoscales horizontally. We've sized for 10x peak load with cold-start optimization.
  • Pub/Sub absorbs traffic spikes. Long tasks queue and are processed by elastic worker pools rather than held synchronously.
  • Per-tenant rate limits prevent any single team from monopolizing capacity.
  • Vector DB sharding per tenant or per high-volume corpus.
  • Cost grows roughly linearly with usage. We project ~$X-Y per active employee per month based on observed usage in pilots.

The architecture is the same at 1,000 or 50,000 employees — what changes is provisioned capacity, not the design.

What's the cost model and how do we control it?Cost

Cost has three drivers, in order of magnitude:

  • LLM tokens (largest, ~70-80% of run cost). Controlled via model routing — Gemini Flash handles 80% of steps; Pro escalates only when needed. Typically reduces token spend by ~60%.
  • Vector DB and storage. Modest and predictable — scales with corpus size, not user count.
  • Compute (Cloud Run, Pub/Sub). Trivial relative to LLM cost in most workloads.

Control levers:

  • Semantic cache: Common queries are served from cached responses (30-50% hit rate typical).
  • Token budgets per task: Hard ceilings prevent runaway loops.
  • Model routing: Cheap-first, escalate when needed.
  • Async batch: Background tasks use cheaper models with longer context windows.
What if Vertex AI or Gemini goes down?Ops
  • Multi-region failover for the agent service and data plane.
  • Secondary LLM provider (Anthropic, OpenAI) configured for critical paths. Switchover via feature flag — no code change needed.
  • Graceful degradation: If LLM is unavailable, the agent returns a clear "service temporarily unavailable" message and queues the task for retry — never fakes a response.
  • Status page + alerts: Users see real-time service status, ops team is paged.
SLO target depends on the use case. For internal productivity, 99.9% (≈8h downtime/year) is typically sufficient. For customer-facing, we'd architect for 99.99% with multi-region active-active.
Can we fine-tune the model on our internal data?Quality

Three options, in increasing complexity:

  • RAG (recommended start): Index your docs, retrieve relevant chunks at query time. Lowest cost, fastest to update, easiest to audit. Sufficient for ~80% of needs.
  • Prompt tuning / adapters: Train a small adapter layer on top of the base model. Captures style and format conventions without touching the base. Good for tone, structure, domain vocabulary.
  • Full fine-tuning: Update the base model weights. Most powerful, most expensive, longest iteration cycles. Required only for narrow specialized tasks.

Recommendation: start with RAG, measure quality, layer in prompt tuning if a gap remains, and only consider full fine-tuning for specific high-value workflows where RAG plateaus.

How quickly can we see this in production?Delivery

Phased rollout, ~3 months end-to-end:

  • Weeks 1–2: Discovery + scoping. Pick the first workflow (highest pain × lowest risk), define success metrics, build the eval set.
  • Weeks 3–6: MVP + pilot. Build the workflow end-to-end, deploy to 5-10 pilot users in draft-only mode. Measure adoption and accuracy.
  • Weeks 7–10: Iteration + expansion. Address pilot feedback, expand to 100+ users, graduate the highest-confidence actions to autonomous.
  • Weeks 11+: Maintenance + handoff. Documentation, runbooks, training. FDE rolls off; your team owns the system.

The first workflow in production is the hardest. Subsequent workflows reuse the platform and ship in weeks, not months.

How do you handle prompt injection from emails or web content?Security

Prompt injection is a real attack vector — adversaries embed instructions in emails, documents, or web pages the agent reads. Defenses are layered:

  • Tagged-content prompts: External content is wrapped in clear delimiters with instructions to treat it as data, not commands.
  • Tool-level scoping: Tools have least-privilege access. Even if a prompt injection succeeds, the tool can't perform unauthorized actions.
  • Output filtering: Suspicious agent outputs (sudden topic changes, requests to email new addresses, unusual data exfiltration patterns) are flagged and reviewed.
  • Input sanitization: Known injection patterns are stripped from external content before ingestion.
  • Continuous red-teaming: We run adversarial test prompts as part of the eval suite.
Prompt injection cannot be fully eliminated — it's an active research problem. We design for containment: assume the model can be confused; ensure the consequences of confusion are bounded.
What about regulatory compliance (GDPR, SOC2, HIPAA)?Security
  • GDPR: Data residency via VPC Service Controls. Right-to-deletion (RTBF) implemented at the data layer (vector DB, Firestore, BigQuery). DPA signed at contract time. Data minimization at ingest.
  • SOC2: Google Cloud is SOC2 Type II certified. We extend with audit logs, access controls, and runbooks. Customer can request our most recent SOC2 report.
  • HIPAA: Optional via BAA (Business Associate Agreement). Several Vertex AI services are HIPAA-eligible. We can scope the architecture to those services for healthcare workloads.
  • Industry-specific (financial, government): Architecture adapts — air-gapped deployments, FedRAMP, etc., depending on requirements.
How do we measure success?Delivery

Three layers of metrics, instrumented from day one:

  • Adoption: % of eligible users active weekly. Target depends on pilot scope; typical mature deployment sees 30-60%.
  • Efficiency: Time saved per task (compared to baseline). Tasks completed per user per week. % of tasks fully automated vs. required human override.
  • Quality: Task success rate (did the agent achieve the goal?). Error rate (incorrect actions taken). User satisfaction (NPS-style feedback after each task).

We review these monthly with you and adjust the prompt library, model routing, and tool registry based on what the data shows.

What's the data retention policy?Cost
  • Prompts and responses: Default 30 days for debugging and quality review. Configurable.
  • Audit logs: Default 90 days; longer if required by your compliance regime (some industries require 7 years).
  • PII: Redacted before storage. The redacted form is what's retained; the originals are not stored.
  • Right to deletion: Implemented via tombstone + cascading delete across vector DB, Firestore, BigQuery, and Cloud Storage. Verified deletion within X days.
  • Documented in DPA: Retention specifics are part of the Data Processing Agreement, customer-tunable.
How do we customize for our specific processes and terminology?Ops

Customization happens at three layers, none of which require model retraining:

  • Prompt library: System prompts are tailored per workflow with your terminology, conventions, and approval policies.
  • Tool registry: Custom tools wrap your internal APIs, CRMs, or ticketing systems. Adding a tool ≈ writing a typed function.
  • RAG corpus: Your internal docs (wikis, runbooks, policy guides) are indexed and retrieved at query time. Updating a wiki page propagates to the agent within minutes.

For highly specialized vocabulary or output format, we layer in prompt tuning — but only if RAG + custom tools don't get us there.
